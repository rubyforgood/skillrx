Topics: where the provider choice goes

The topics list shows one provider's topics at a time. People who work with more than one provider (every administrator, and contributors with several) choose which one. Today that choice sits below the search and filters, with its label beside the dropdown instead of above it. Each option below is the same screen with the same data; only the provider control moves. Menus in A and C open when you select them.

D: provider as a filter, with All providers (revised recommendation)

  • It's the first filter, labeled above like the others. Search, Provider, Filters and Clear filters share one row and one label style. It stays visible rather than folding into Filters, because it changes the most and it decides the rest.
  • All providers is the first option and the default for anyone with more than one provider. Every provider is in the list, including the current one.
  • A Provider column appears only when All is chosen. With one provider chosen, every row would say the same thing. Try switching the field above: the column comes and goes.
  • Plain text, not a badge. The design system keeps pills for status (Active, Archived), where color means something. Provider is a name with no state, and colored badges for an open-ended list of providers would run out of distinguishable colors and fail "never color alone". GitHub's repository column, Jira's project column and Linear's team column are all plain text.
  • Clear filters resets it to All providers, like every other filter. The last choice is still remembered between visits, as today.
  • People with one provider don't see the field.

What it changes beyond this page: today a contributor's new topic is saved under the chosen provider, because the topic form only shows a Provider field to administrators. With All, a contributor who has more than one provider needs that field too (required, defaulting to the provider they last chose). Contributors with one provider see no change.

What's wrong today

  • The label is in the code, but not where labels go. "Switch provider" is a real <label for="provider_id">, so screen readers announce it. But every other field on the page has its label above it, and this one sits to the left at desktop width and jumps above at phone width. The design system puts labels above fields so the eye reads one column.
  • It's worded as an action, not a name. A label names the value in the field ("Provider"). "Switch provider" describes what you'd do, and reads oddly once you've chosen.
  • The dropdown doesn't contain the provider it shows. The current provider is the prompt text, and the list holds only the others. You can't see the full set, and you can't tell which one is current once it's open.
  • It's in the wrong place in the hierarchy. The provider decides which topics exist on this page. Search and filters narrow those topics down. The broader choice sits below the narrower ones, on its own row, so the controls run Search → Filters → Provider → table, three bands that don't line up.
  • It's said twice. The subtitle says "From Provided by the government" and the dropdown says it again one row down.

The rule that decides it: scope before filters

Provider isn't a filter. It's remembered across visits (a cookie), it decides which provider a new topic belongs to by default, and "Clear filters" doesn't and shouldn't reset it. Products separate "which set of things am I in" from "narrow this set down": the first sits with the title, the second sits in the toolbar. GitHub puts the repository and branch above the file list, Google Analytics puts the property at the top of every report, Stripe and Vercel put the account or team in a switcher, and Shopify's Polaris keeps saved views above the filters. None of them put the scope inside or below the filter row.

The options

OptionWhat it isWho does thisCost
A: in the page header (recommended) A "Provider: name ▾" button replaces the subtitle under "Topics". It opens a menu of every provider, with a check on the current one. The toolbar is left with search, Filters and Clear filters on one row. GitHub branch and repository pickers, Google Analytics, Grafana dashboards, Atlassian project pickers. One new small control (a menu). The provider stops being a form field, so it no longer needs a field label: the visible "Provider:" is part of the button's name.
B: first field in the toolbar Provider becomes the first field in the toolbar, labeled above like Search, so everything sits on one row. Polaris index filters, Jira issue search, many admin tables. Cheapest: a CSS and label change. But it makes the scope look like a filter, so people will expect Clear filters to reset it. It also crowds the row: at desktop the row is full before Filters.
C: switcher in the rail A provider switcher at the top of the navigation, like a workspace or team switcher. Linear and Slack workspaces, Vercel and Netlify teams, Stripe accounts. Says "this changes the whole app", which isn't true: only Topics uses it. Beacons and the Administration pages would sit under a provider switcher that does nothing to them. Hidden in the drawer on phones.

Why A

  • Scope sits with the title, filters sit with the list. "Topics · Provider: Provided by the government" reads as what you're looking at; the row below is how you narrow it.
  • The toolbar becomes one row at desktop: Search, Filters, Clear filters, with labels above, the same as every other list in SkillRx.
  • It's said once. The button replaces the "From …" subtitle.
  • The menu shows every provider with a check on the current one, which fixes the missing-option bug. With more than about seven providers it gets a filter box at the top, as the design system's combobox does.
  • People with one provider see plain text ("Provider: Community health clinic"), not a control that can't change anything.
  • Built from what's there: <rfg-menu> with a secondary <rfg-button> trigger. Choosing an item submits the same form to the same endpoint, so the controller doesn't change. Without JavaScript the menu items are still buttons in a form.
